# 2026-11-25：503 日志未计数导致切换不触发

## 原因与影响

北京时间 2026-11-25 00:21:00–00:30:59，New API 原始日志中，渠道 #75 有 41 个 503 请求，#76 有 130 个。切换服务在此期间没有记录任何事件。

当时已启用的 `gpt` 配置使用 #75，规则为 10 秒内 3 次，候选为 #75、#48、#73、#59、#66。仅从 00:21 开始回放，#75 在 00:21:05、00:21:08、00:21:10 的三个独立请求就已满足阈值，应开始测试备用渠道。能否成功切换还取决于备用渠道当时的测试结果，不能仅凭历史错误断言它一定可用。

旧解析器要求日志出现英文 `record error log` 或 `channel error`。实际 New API 日志已使用中文 `记录错误日志` 和 `渠道请求出错`，导致 503 识别为 0 次。HTTP 服务和定时巡检仍正常运行，因此健康检查无法揭示这个漏计问题。

#76 没有纳入该切换配置，其错误不参与 #75 的阈值；这与 #75 本身的日志识别故障是两件事。

## 修复后的识别规则

识别渠道 ID 与 503 状态码字段或固定结构，不要求特定语言的说明文字：

```text
任意说明: channelId=75, content=status_code=503, unavailable
任意说明 (任意 #75，任意 503): unavailable
```

第一种日志使用 `channelId` 与 `content=status_code` 字段；第二种使用括号内的 `#渠道ID`、分隔符和 503 状态码，兼容半角、全角逗号与冒号。502、504、5030、响应正文中单独出现的 503、缺少渠道信息的访问日志不触发计数。

保留原有滚动窗口和请求去重逻辑：同一渠道同一请求 ID 的渠道错误行与记录错误行只计一次；只累计当前受管渠道；达到阈值后才测试候选并切换。服务首次启动跳过历史日志，修复上线不会重放凌晨错误并据此切换。

同步保留此前线上已有的删除渠道处理：选优时移除已删除的候选，状态事务忽略已删除备用渠道但仍校验目标存在，后台列表过滤已删除候选。
